## 1. Summary

This spec captures the remediation work for the production-readiness audit completed on 2026-07-28. The audit identified **17 confirmed issues** (6 critical, 5 high, 4 medium, 2 low) plus several untested residual areas. The fixes are grouped into the smallest safe batches that can be verified independently and are ordered to address the highest production risk first.

## 2. Goals

1. Make the application safe to run in a multi-instance / serverless production environment.
2. Enforce consistent, server-side tenant and RBAC authorization on every store-scoped and org-scoped operation.
3. Remove unbounded queries and in-memory scalability bottlenecks from admin and billing paths.
4. Ensure production secrets/configuration cannot silently fall back to unsafe defaults.
5. Wire the background worker into the production deployment topology.
6. Preserve all existing passing build, typecheck, lint, and test gates.

## 3. Non-Goals

- Rewriting the authentication strategy (e.g., switching to session cookies) is out of scope.
- Adding brand-new product features (e.g., full invite flow, audit log UI) is out of scope.
- Live load testing, penetration testing, and third-party integration end-to-end verification are out of scope for this coding task.

## 4. User Stories

- As an operator, I want background jobs and webhooks to be processed exactly once across any number of app instances.
- As an admin, I want project and team management to respect role hierarchy and seat limits.
- As a store staff member, I can only act on the store I am assigned to.
- As a platform owner, I want reset/MFA emails to be delivered in production, not logged to console.

## 5. Domain Model

No new domain entities. Reuses existing `User`, `Organization`, `Store`, `Project`, `ProjectMember`, `Role`, `Integration`, `SaaSCoupon`, `VerificationToken`, `DailyAction`.

## 6. Public Contract

- `src/modules/organizations` exports `tenantGuard.assertStoreAccess(user, storeId)` and `tenantGuard.assertOrganizationAccess(user, organizationId)`. Other modules may use these through the public barrel only.
- `src/modules/auth` continues to export `requireUser`, `requireRole`, `requireSuperAdmin`.
- `src/shared/events` continues to export `eventBus` and `DomainEvent`.

## 7. Data / Persistence

- Add `@@index([subscriptionId])` or `@@unique([subscriptionId])` on `Organization`.
- Add `@@index([aiRepliesResetAt])` on `Organization` (if not already present).
- No other schema changes required; migrations must be generated with `npx prisma migrate dev`.

## 8. API / UI Surface

All server actions and server components that accept a `storeId` must verify authorization with `tenantGuard.assertStoreAccess`. Mutating actions must require a role of at least `STORE_OWNER` unless the action is explicitly designed for `STAFF` and scoped to their assigned store.

## 9. External Integrations

- `REDIS_URL` becomes a production-required environment variable.
- `EMAIL_PROVIDER` cannot be `console` in production.
- Stripe webhook billing lookup must query by indexed `subscriptionId`.

## 10. Edge Cases & Failure Modes

- Redis unavailable at startup: production should fail fast, not silently use in-memory state.
- Staff user with `organizationId` but no `storeId`: must be able to view org-level pages but denied store-scoped mutation/read of stores not assigned.
- Duplicate Stripe/Meta webhooks: idempotency keys must be stored in Redis with TTL.

## 11. Security & Privacy

- No secrets logged.
- No PII exposed in error messages.
- Authorization checked server-side; never trust client-supplied `storeId` alone.

## 12. Testing Strategy

- Unit tests for new domain helpers (e.g., role/tenant guard edge cases).
- Integration tests for repositories that enforce seat limits and indexed lookups.
- Existing `npm run test` must pass; add targeted tests for changed actions.
- Manual verification: `npm run build`, `npm run typecheck`, `npm run lint`.

## 15. Batch 2 — Redis-backed runtime state

### 15.1 Scope

Re-land the Redis-backed implementations for the in-memory runtime state that breaks in multi-instance deployments:

- `EventBus` in `src/shared/events`
- `RateLimitStore` in `src/shared/security`
- Meta webhook deduplication in `src/modules/meta/infrastructure/webhook-guard.ts`
- Harden `src/shared/queue` production fallback

### 15.2 Design

- Add `src/shared/redis/client.ts` as the single server-only `ioredis` entry point. It returns a shared Redis connection and is only imported by server-side modules (queue, rate limiter, webhook guard, event bus).
- `RedisEventBus` uses Redis Pub/Sub: each process keeps a publisher and a subscriber on `omniconnect:events`. `publish()` dispatches local handlers first, then publishes the serialized event to Redis. Received messages are deserialized and dispatched to local handlers. If Redis is unavailable, local handlers still run and the Redis publish error is logged.
- `RedisRateLimitStore` uses an atomic `INCR` + `PTTL` Lua script to implement a fixed-window counter with `PEXPIRE` on the first hit.
- `webhookGuard` uses Redis `INCR`/`PEXPIRE` for per-IP rate limiting and `SET ... PX ... NX` for payload hash idempotency. In-memory maps are retained only as a dev/test fallback when `REDIS_URL` is not set.
- `getQueue()` throws in production if `REDIS_URL` is missing; dev/test may still use the in-memory queue fallback.

### 15.3 Runtime safety

- Fail-fast for missing `REDIS_URL` in production is handled by `validateProductionSecrets()` in `instrumentation.ts` and by explicit checks inside runtime guards. `next build` static generation must not attempt Redis connections, so `RedisEventBus` creates connections lazily on the first `subscribe`/`publish`.
- `ioredis` is listed in `next.config.ts` `serverExternalPackages` so it is not bundled into the middleware/client output.

## 16. Batch 3 — Medium/low polish

### 16.1 M4 — Remove password reset code from URL

The password-reset email currently links to `/reset-password?email=...&code=...`, exposing the 6-digit reset code in browser history, server logs, and referrers.

- Change the email link to `/reset-password?email=...` only, keeping the 6-digit code in the email body.
- `reset-password-form.tsx` pre-fills `email` from the query string but no longer pre-fills `code`; the user enters the code manually.
- `resetPasswordAction` continues to verify the code via `verificationCodeService.verifyCode`.

### 16.2 L1 — Migrate from `next lint` to ESLint CLI

`next lint` is deprecated and will be removed in Next.js 16. Add an `eslint.config.js` (or `.mjs`) that extends Next.js' recommended flat config and update `package.json` `lint` script to `eslint .`.

### 16.3 L2 — Resolve Vitest CJS deprecation warning

The Vitest CJS Node API warning is cosmetic; address by ensuring Vitest config uses ESM (`.ts` or `.mjs`) and that `package.json` does not override `vite` to a CJS build.

## 17. Batch 4 — Structured per-field server validation errors (M2)

### 17.1 Scope

Start with the project management surface (`project-actions.ts` and `/projects/page.tsx`), which currently only shows a single top-level `error` string even when `safeParse` can identify which fields failed validation. This is the first increment of M2; other forms can follow the same pattern.

### 17.2 Design

- Extend `ProjectActionState` to include `fieldErrors?: Record<string, string[]>` and `formError?: string`.
- When `safeParse` fails, return `zod` `flatten().fieldErrors` instead of `issues[0].message`.
- In `/projects/page.tsx`, render per-field errors under each input and set `aria-invalid` / `aria-describedby` for accessibility.
